# Plan: Pi as a Worker Backend in the Runtime

Slug: `pi-worker`. Living spec: `docs/specs/harness-adapters.md`. Status: APPROVED 2026-11-07

## Why now

The runtime knows two worker families, `claude` and `codex` (`server/profiles.py:8`), and supports Pi as a **lead
only** (R178, `docs/specs/harness-adapters.md:47`). Four things block a Pi worker today: a `pi` family is not in the
allow-list, `spawn` builds no Pi argv, the host policy refuses every non-lead Pi session, and Pi's MCP registration
was emptied, so a Pi worker has no `report` tool at all. Until all four are gone, the open orchestration plans in the
`agent-skills` repo cannot run on Pi workers. The user's decision (2026-11-07): Pi is a **native family** (no `pi`
profile), the worker tools come from Pi's MCP registration, and the review gates keep `gpt-6.1-terra` as the brain.

## Scenarios

- **S1** WHEN a spawn names the pi family with a model and an effort, THEN the runtime launches `pi --print --model <model> --thinking <effort>` with the task last, and the task carries the role line and the report protocol.
- **S2** WHEN a spawn names the pi family, THEN the worker's environment carries `MINIMAX_API_KEY` and the Pi provider variables, and a claude or codex spawn carries neither.
- **S3** WHEN a Pi worker calls `report` for its own assignment, THEN the runtime accepts the report instead of refusing the session.
- **S4** WHEN a Pi worker calls `spawn`, `stop` or `resume`, THEN the runtime refuses the call with a reason that names the host policy.
- **S5** WHEN a Pi worker calls a team-scoped tool for a worker outside its own team, THEN the runtime refuses the call.
- **S6** WHEN a spawn names the pi family with an effort, THEN Pi receives `--thinking` with the same level, and an effort Pi does not know is refused before anything starts.
- **S7** WHEN a Pi spawn names a directory outside the operator's authorised paths, THEN the spawn is refused and no worker starts.
- **S8** WHEN a Pi worker reports, THEN the report binds to its assignment and the lead's team receives exactly one result.
- **S9** WHEN Pi starts a worker session, THEN the `agent-runtime` MCP server is registered in Pi's MCP configuration, so the worker holds `mcp__agent-runtime__report` from its first call.

## Out of scope

- A `pi` profile, and any change to the `minimax` Claude profile (D1, D2).
- A Pi extension: no Pi-side tool registration, no Pi-native agent definitions (D3, D4).
- Token accounting for Pi workers; the spec records that Pi has none.
- The `agent-skills` driver — the Pi backend, the brain tier and the Pi model column: `agent-skills/docs/plans/2026-11-07-pi-worker-driver.plan.md`.
- The dotfiles commit that adds a Pi column to `~/.claude/CLAUDE.md`; the driver falls back to its own table until then.

## Risks

- **Security:** a Pi worker is a host the server authorizes itself (D5). Its tool set is a fixed allowlist inside its own team, the authorised-directory guarantee is unchanged (S7), and the report path is the runtime's own (D3). A Pi worker inherits `MINIMAX_API_KEY` (D7) — a credential a Claude or Codex worker never receives.
- **Performance:** one extra process layer per worker (Pi's own session), no change to the dispatch store's polling or its schema.
- **Migration:** no durable-state change — the dispatch store, the assignments and the team binding are untouched (S8). The only ledger change is the spec amendment (D6).
- **Rollback:** dropping `"pi"` from `BUILTINS`, the Pi branch in `spawn` and the worker allowlist in the host policy returns the runtime to today's behaviour; the spec amendment is reverted with it.

## Seams

- `tests/test_pi_worker.py` (new), beside `tests/test_pi_lead.py`: the highest existing seam for a Pi session — the runtime's own tool functions (`hc_tools.spawn`, `host_policy.authorize`) with the same fakes.
- `tests/test_tools.py` for the spawn argv and the provider scrubbing.
