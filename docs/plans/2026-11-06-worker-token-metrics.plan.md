# Plan: worker token metrics, Codex worker profile

Slug: `worker-token-metrics`. Living spec: `docs/specs/agent-runtime.md`. Status: APPROVED 2026-11-06.

## Why now

1. **A Codex worker does not run the policy the fleet thinks it runs.** `codex_instructions()` (`server/hc_tools.py:137-155`) reads only `developer_instructions` from `~/.codex/agents/<agent>.toml`; that file's model, effort and sandbox are ignored. The spawn argv (`server/hc_tools.py:329-332`) is `codex --no-daemon <model> <prompt>` — no profile. The evidence is in the T6 rollout: effort `medium`, `approval_policy: on-request`, `auto_review` in `turn_context`, even though `implementer.toml` said `high`. The dotfiles PR ([#7](https://github.com/FBisca/dotfiles/pull/7)) adds `agents/.codex/worker.config.toml` (`approval_policy = "never"`, `sandbox_mode = "workspace-write"`, `model_reasoning_effort = "medium"`) plus the global `model_auto_compact_token_limit = 150000` and `tool_output_token_limit = 7000`. The runtime has to name the profile or none of it applies.
2. **Worker cost is invisible.** T6 (Codex `gpt-6.1-terra`) burned **101M input tokens**, 108,808 output tokens, peak context **372,087**, 427 tool calls — of which **30% were polls** — across ~2,000 changed lines in 38 files, and no compaction. Nothing in the runtime shows that. `wait` and `status` report state, not cost, so a config change is judged by guesswork.
3. **"Before" and "after" must come from the same code.** The baseline exists only as a hand-run script over one log. Unless the parser that measures a live worker is the parser that measures the baseline, the comparison is an anecdote.

The two halves belong together: `-p worker` is the change being judged, and the metrics are the judge. The dotfiles PR lands first; the runtime needs both halves to answer "did the profile change anything?".

## Scenarios

- **S1** WHEN the runtime spawns a Codex worker and the worker profile is usable, THEN the launch argv contains `-p worker` between `codex --no-daemon` and the prompt.
- **S1a** WHEN a spawn records its worker, THEN the record carries the checkout's cwd, its base commit (null outside a git repository) and the spawn time, and both the base commit and the spawn time are read before the worker starts.
- **S1b** WHEN the runtime reads a worker's record, THEN it returns the record it wrote, and nothing for an unknown or unsafe worker name.
- **S1c** WHEN the worktrees directory is a symlink, THEN the record is refused rather than written through the link.
- **S1d** WHEN a record carries a field that cannot be serialized, THEN the record is dropped and the spawn is unaffected.
- **S2** WHEN the worker profile file is missing, or the base `config.toml` carries a legacy `[profiles.*]` table, THEN the worker still starts without `-p worker`, and a dispatch-enabled spawn's per-worker metadata records `profile_applied=false` with the reason.
- **S2a** WHEN `hc` refuses the spawn, or the worker's task was not sent, THEN no record is written.
- **S2b** WHEN the worker is a Claude worker, THEN the argv carries no `-p` and the record's Codex profile fields are null.
- **S2c** WHEN the override names a profile whose file is missing, THEN the reason is `missing_file`; and an unsafe override name is refused without writing anything outside the state directory.
- **S2e** WHEN a spawn is cancelled and its terminal survives, THEN the worker is still recorded.
- **S3** WHEN a Codex worker's session log is parsed, THEN the recorded approval policy, reasoning effort, sandbox mode and model come from that session's own `turn_context` records.
- **S4** WHEN the runtime binds a Codex assignment to a session log, THEN it matches the log whose first prompt user message carries that `assignment_id`, and never a log belonging to another assignment.
- **S4a** WHEN the log's first user record is a CLI-injected context block that carries no assignment marker (Codex writes its `environment_context`/AGENTS.md record before the prompt), THEN the binding skips it and matches the prompt record that follows, instead of rejecting the log.
- **S5** WHEN the runtime binds a Claude assignment to a transcript, THEN it matches the transcript whose first user message carries that `assignment_id`, and the runtime's session-id fallback reads `CLAUDE_CODE_SESSION_ID`.
- **S5a** WHEN the runtime computes its own identity and finds no CLI ancestor, THEN the session-id fallback reads `CLAUDE_CODE_SESSION_ID` — the variable that is actually set — and not the unset `CLAUDE_SESSION_ID`.
- **S6** WHEN a Codex session log is parsed, THEN the result carries input, cached, output and reasoning tokens, peak context, compaction count, tool calls by kind and wall time.
- **S7** WHEN a Claude transcript is parsed, THEN the result carries the same fields, taken from the per-message usage and the tool calls in the transcript.
- **S8** WHEN a Codex tool call is classified, THEN the classification reads the `tools.<name>` the call invokes and the `cmd:` string it carries, so a `write_stdin` poll is counted as a poll and not as a read.
- **S9** WHEN the lead calls `wait`, THEN every returned assignment carries one metric line — context and peak, input, output, calls with the poll share, and the diff — and an assignment whose log cannot be read carries "no metrics" instead of failing the wait.
- **S10** WHEN the lead calls `status` for a worker, THEN the record carries the same metric line for that worker.
- **S11** WHEN a worker publishes a completing report, THEN exactly one JSONL row is appended to the ledger with the assignment, worker, cli, model, effort, approval policy, sandbox, token counts, peak context, compactions, calls by kind, wall time, diff and outcome — and with no prompt text, no file content and no tool arguments.
- **S12** WHEN the runtime measures a worker's diff, THEN it runs git in the worker's checkout against the base commit captured at spawn, so committed work counts, and the worker is never asked for the number.
- **S13** WHEN the baseline script runs over the Nov 5–6 session logs, THEN it uses the same parser and prints the same fields, so before and after are comparable.
- **S14** WHEN the wait batch would exceed its base byte cap with the metric lines attached, THEN the lines are omitted and the wait still returns its messages.
- **S15** WHEN the tool list is published, THEN the tool descriptions and parameters still total at most 400 words, and the tool schema is unchanged.
- **S16** WHEN a session log is missing, unreadable, truncated or unparseable, THEN no spawn, wait, status or report fails; the metrics are simply absent.

## Out of scope

- The agent-skills changes named in the handoff: the `Read` column and line estimate in `skills/start-planning`, the "new scope = new ticket + new worker" rule and section-only briefs in `skills/orchestrate`, token metrics in `docs/workflow.md` step 10.
- The diff-size tripwire: the runtime measures the diff (D13); what the orchestrator does with it is a later decision, and it costs no extra worker calls.
- The global Codex limits (`model_auto_compact_token_limit`, `tool_output_token_limit`) — dotfiles' side.
- Installing or editing anything under `~/.codex` or `~/.claude` (D19).
- A new MCP tool, a new hook, or any change to the dispatch store's schema (D20).
- Storing prompt content, file content or tool arguments in the ledger or the metadata (S11).
- Comparing workers across different models or efforts — the ledger records them so a later slice can, but no comparison is built here.

## Risks

**Security.** The parsers read session logs, which contain the worker's prompts, file contents and command output. The rule is one-directional: read the log, never copy from it. The ledger and the metadata carry counts, model names, paths and git numbers — no prompt text, no tool arguments, no diff content (S11). Both files are written 0600 under the state root, and the state root is created 0700. The binding searches a user's own `~/.codex/sessions` and `~/.claude/projects` trees by an assignment id the runtime itself minted; the match is a literal string comparison, never a regex, so a log cannot inject anything into the query. The diff is measured by `git diff --shortstat` in the worker's checkout, and only the numbers are kept. A worker cannot write the metadata of another worker: the file is keyed by the worker's own terminal name, which `hc` refuses to duplicate.

**Performance.** A Codex rollout for one task reached 5.4 MB / 2,877 lines, and the fleet's logs run to hundreds of files. Parsing on every `wait` would be wasteful, so the parser is incremental: it reads from the last offset it consumed, keyed by the log's path and size, and keeps running counters. The binding caches the resolved log path per worker in the metadata file, so the candidate scan runs once per assignment. The candidate scan lists the session tree and stats each candidate, but only a candidate created at or after the spawn is read, and only its head (256 KB) — so an unbound assignment costs one listing plus one bounded head read per recent candidate, not a walk over every log's contents. A wait that has to parse a 5 MB log pays it once per log growth, not once per wait.

**Migration.** There is no schema migration: the dispatch store, the tool schema and the hook set are untouched (D20). The new state lives in two new places under `$XDG_STATE_HOME/agent-runtime/`: `usage.jsonl` and `worktrees/`. Both are additive; deleting them restores the previous behaviour exactly. The risk that remains is a source collision: `server/dispatch_store.py` is being edited by the predecessor plan's T2 on another branch, so this plan avoids that file entirely (D12), and `server/hc_tools.py` is edited by both plans — T1 and T2 here touch only the spawn argv and the identity fallback, well away from T2's registration code. The dotfiles PR must land before `-p worker` changes anything; until then the profile check finds no file and records `profile_applied=false` (S2).

**Rollback.** Three independent levers. Drop `-p worker` and Codex workers run exactly as they do today. Delete `server/usage.py`'s call sites in `wait`, `status` and `report` and the surfaces return to their current shape. Delete `usage.jsonl` and `worktrees/` and no state remains. No data is moved, no table is dropped, no file format is published — the metadata and the ledger are written by this plan and read only by this plan.

## Seams

- **Launch argv** — `server/hc_tools.py:329-338` builds the CLI argv; D1/D3 change the Codex branch and the flag lands there. `server/hc_tools.py:342-344` appends the `assignment_id` the binding relies on.
- **Identity fallback** — `server/hc_tools.py:179-194` (`dispatch_identity`) reads `CLAUDE_SESSION_ID`; D7 corrects the name.
- **Per-worker metadata** — written by the lead at spawn (`server/hc_tools.py:338-344`, after `store.register`) and updated by the worker on completion; read by the lead at `wait`/`status`.
- **Wait surface** — `server/hc_tools.py:534-590` returns the batch from `server/dispatch_wait.py:98-145`; the metric lines attach to the batch's assignment rows, keyed by the row's `name`, after the store read. `server/dispatch_store.py:630` is where the base byte budget is computed — the lines are added after it and guarded by S14, so the store is not edited.
- **Report surface** — `server/hc_tools.py:680-700` publishes the report; the ledger row is appended there, on the completing kinds.
- **Status surface** — `server/hc_tools.py:710-712` calls `lib.status` (`server/agent_runtime.py:417`); the metric line rides on that record, which R11 defines.
- **Word budget** — `server/mcp_server.py:31-74` and `tests/test_mcp_server.py:133-146`; untouched by D10.
- **Session logs** — Codex: `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<thread_id>.jsonl`. Claude: `~/.claude/projects/<cwd-slug>/<session_id>.jsonl`.
- **The dotfiles side** — `~/developer/dotfiles` PR #7 (`agents/.codex/worker.config.toml`), installed to `~/.codex/worker.config.toml`.
- **Living spec** — `docs/specs/agent-runtime.md`: R11 (status record), R99 (word budget), R130 (the Codex argv) are amended; the new requirements are appended at the numbers the archive step assigns.
