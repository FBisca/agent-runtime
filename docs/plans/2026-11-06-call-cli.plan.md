# Plan: `agent-runtime call` — the dispatch tools from a script

Slug: `call-cli`. Living spec: `docs/specs/agent-runtime.md`. Status: ARCHIVED 2026-11-06.

## Why now

The orchestrate lead loop moves into code (agent-skills plan `code-driven-orchestrator`). An LLM lead cost 220M cache-read tokens over 1,232 Opus turns on one run (user-measured, 2026-11-06), almost all of it bookkeeping around `spawn`/`wait`/`resume`. A script can't call the MCP tools today: `bin/agent-runtime` has only `resolve`, `contract`, `status`, `list` (server/agent_runtime.py:496-515).

## Scenarios

- **S1** WHEN `agent-runtime call <tool> --lead L --json '<args>'` runs in an hc terminal, THEN it runs that dispatch tool and prints the tool's JSON result on stdout and exits 0.
- **S2** WHEN the tool returns an error result, THEN the CLI prints it as JSON on stdout and exits 1.
- **S3** WHEN the caller is not an hc terminal, THEN the CLI exits 2 with the `require_hc` message and starts nothing.
- **S4** WHEN `--json` is not valid JSON or the tool name is unknown, THEN the CLI exits 2 with a usage message and starts nothing.
- **S5** WHEN two separate `call` processes pass the same `--lead`, THEN `wait` in the second sees and receives reports for assignments spawned by the first.
- **S6** WHEN a subagent runs `agent-runtime call <tool>` through Bash, THEN the PreToolUse hook denies it; WHEN a non-subagent runs it with a mutating tool, THEN the hook asks.
- **S7** WHEN `call` runs with a `--lead` different from the generation of the terminal's latest team and that team has unfinished assignments, THEN it exits 2 naming the live generation, starts nothing, and the other generation's `wait` still receives its reports.

## Out of scope

- Session-id resume of dead panes (orchestrate starts a fresh worker instead).
- Any change to MCP tool behaviour.

## Risks

- Security: the hc-terminal check is unchanged (S3); the Bash hook gates `call` like the MCP tools (S6); a second generation cannot evict a live one (S7).
- Performance: n/a (one process per call).
- Migration: n/a (no store schema change).
- Rollback: delete the subcommand; nothing else depends on it until orchestrate's driver ships.
