## Why now

The pipeline delivers tickets, not outcomes. A plan is archived when every ticket merges; nothing checks that the
plan's goal holds on the integrated code. The only deterministic gate, `converge`, greps test *names* for scenario IDs
and checks changed files against Paths: `assert True` in `test_S3_x` passes it. The worker's `verified` flag in
`attempts.jsonl` is its own claim. Meanwhile the plan is parsed by four readers that drift (driver, engine converge,
skill converge, Herdr panel), the authored plan doubles as the driver's mutable status board, and `docs/plans` /
`docs/specs` are hardcoded in five places.

## Design

### Files and discovery

```
<plan dir>/                      # found by D8; any directory, hidden or not, in or out of the repo
  2026-11-10-<slug>.plan.yaml    # the contract (approved, digested)
  2026-11-10-<slug>.plan.md      # the narrative (not digested)
  2026-11-10-<slug>.oracle/      # oracle payloads, non-discoverable suffix: test_x.py.oracle
<state>/                         # ~/.local/state/orchestrate by default; never in the repo
  approvals/<digest>/            # the approved bytes (D26)
  <repo-key>/<slug>.json         # the ledger: status, gates, decisions, receipt hashes
  <repo-key>/<slug>/receipts/    # receipts and logs, written only by the driver
```

Nothing is created until the first plan is written. No config file is introduced; `--repo` covers plans outside the
repository.

### The contract (`plan/1`)

The YAML file beside this one is the reference instance. Fields:

- top: `schema`, `slug`, `goal`, `spec`, `outcome` (scenario IDs, ≥1, each with evidence), `scenarios`, `tickets`,
  `approval` (written by `plan approve` only).
- scenario: `id`, `when`, `then`, optional `evidence`.
- evidence: `check` + `baseline` (`pass` | `fail`), optional `oracle` (files in the oracle dir), `place` (repo
  directory they are copied to, suffix `.oracle` stripped), `timeout`, `env` (names), `negative` (a patch file in
  the oracle dir), `promote` (default true); or `human: <what a person confirms>`.
- ticket: `id`, `delivers`, `satisfies`, `paths`, `size`, `difficulty`, optional `blocked_by`, `owner` (default
  `agent`), `risk`, `evidence_waiver`, `max_fix_rounds`, `repo` (only for non-agent owners).

Derived, never written: the md path, readiness, routes, the spec dir, every status. The loader rejects unknown and
duplicate keys.

### Verification: one gate, two layers

**Built-in invariants** (code, always on, never declared; they replace converge):

| Invariant | When | Replaces |
|---|---|---|
| Approval: plan and oracle bytes match the snapshot | launch, every round, acceptance | `Status: APPROVED` |
| Scope: changed files ⊆ ticket paths | ticket gate | converge `scope` |
| Integrity: no ticket touches the plan, an oracle or an oracle place | ticket gate | new |
| Covers: every satisfied scenario maps to existing, changed test nodes; CI green at that head runs them | ticket gate | converge `coverage`, `tagged` |
| Spec: every scenario has a requirement line with its provenance, and every Coverage node exists | archive | converge `spec` |
| Receipts: bound to digest and tree, hash in the ledger | acceptance | new |

**Executable evidence** (declared in the plan, run by the driver's runner):

| Phase | What runs | Where |
|---|---|---|
| baseline | every evidence item | `base`, at `plan approve` |
| ticket | evidence of scenarios a risk-tagged ticket satisfies, and outcome evidence at the ticket that completes it | the ticket head |
| integration | every evidence item | one pinned default-branch SHA containing every merge |
| mutation | uncalibrated outcome oracles, with one reviewer-written mutation | the integration SHA |
| archive | outcome evidence | the archive head |

### Ticket EEC routing policy

1. A ticket with no `risk` runs the invariants, its covers, the reviewer and CI. No evidence. This is the default.
2. A ticket tagged `security`, `concurrency`, `retry-idempotency`, `migration`, `external` or `state` must satisfy a
   scenario with evidence, or carry `evidence_waiver`. Good waivers name where the risk *is* verified (an outcome
   item at integration, a trusted existing test); "low risk" is not a waiver.
3. The ticket that completes an outcome scenario runs that outcome's evidence, whatever its risk.
4. Prefer reusing an existing test or a command over a new oracle (the ladder). A new test oracle per ticket is
   never the default.
5. A waiver needs no extra step: it is in the digested plan, so the human approves it with the plan.

### The oracle ladder (how the planner writes evidence before the code exists)

reuse an existing test → command over an observable → black-box test at an existing seam → contract-first test
against an interface a Decision row fixes → human. An oracle may target only an interface that exists or a Decision
fixes; when neither holds, the decision is open and goes back to grilling. Oracles drive the outermost stable seam
(CLI, HTTP, MCP tool, public entry point, the suite's own fixtures) and import the system under test lazily, so they
collect cleanly at base. If a needed fake cannot express a case, the oracle carries a local adapter rather than
waiting for a future fake.

### What the final evidence proves, and what it cannot

| Proves | Does not prove |
|---|---|
| The declared observables hold on the exact integrated tree, run by the driver, not claimed by an agent | Behaviour the oracle does not observe; semantic completeness from finite cases |
| The oracle's assertions bite (controls; calibrated red or a killed mutation) | That the mutation chosen was the most telling one |
| The contract that ran is the one a person approved | Anything against a hostile same-user shell (D26) |
| A human item was confirmed by a named person on a named tree | That the person checked carefully |
| Promoted oracles are in the repo byte-identical | That every CI configuration collects them (the archive receipt runs them explicitly) |

## Worked examples

### 1. Small mechanical refactor (remove the dead `wait_checks.py`)

```yaml
outcome: [S1]
scenarios:
  - id: S1
    when: wait_checks.py is removed
    then: the whole suite passes and nothing imports it
    evidence:
      check: 'uv run --frozen --all-packages pytest -n 4 -m "" -q --junitxml="$EEC_JUNIT" && ! git grep -n wait_checks -- "*.py"'
      baseline: fail          # the grep half fails at base
tickets:
  - {id: T1, delivers: remove wait_checks, satisfies: [S1], paths: [packages/agent-orchestrator/], size: small, difficulty: simple}
```

No risk tag, no ticket evidence; T1 completes S1, so S1 runs at its gate (rule 3) and again at integration. No new
oracle file, no mutation. Failure: a leftover import ⇒ the grep fails ⇒ fix round naming the file.

### 2. User-facing feature (`plans list --json`, this plan's T2)

Contract-first: the command, its flags and its JSON shape are a Decision; the oracle is a CLI test in a temp repo
(two layouts, ambiguity, none) with controls for its JSON assertions. Baseline: uncalibrated (unknown subcommand),
controls pass ⇒ approve accepts it and records "uncalibrated". Integration: PASS, then the mutation check (for
example, the reviewer drops the hidden-directory branch) must turn it red. Failure: the mutation survives twice ⇒
the item becomes human; the plan can only reach ACCEPTED_WITH_HUMAN.

### 3. High-risk orchestration change (stale report after reassignment)

```yaml
  - id: S4
    when: a released worker's report arrives after its unit was reassigned
    then: the report is refused, the unit completes once from the new worker, and attention.md names the stale report
    evidence:
      check: uv run --frozen --all-packages pytest packages/agent-orchestrator/tests/test_stale_report.py -m integration -q --junitxml="$EEC_JUNIT"
      oracle: [test_stale_report.py.oracle]
      place: packages/agent-orchestrator/tests/
      baseline: fail
tickets:
  - {id: T2, delivers: refuse stale reports, satisfies: [S4], risk: [concurrency, state], paths: [...], size: regular, difficulty: complex}
```

The oracle uses `RunFixture` and `fake_runtime` (existing seam), scripts the late report, and asserts one COMPLETE
in the ledger, the refusal, and the attention line. Today's driver accepts the late report, so the baseline is a
calibrated assertion failure. T2 is risk-tagged ⇒ S4 runs at its gate; FAIL ⇒ fix round with the command and log
tail; the worker reruns it locally (no receipt); the driver's rerun decides. Integration reruns it on the pinned SHA.

### Rejections (the outcome oracle of this plan exercises each)

| Attempt | Refused by | Where |
|---|---|---|
| `check: true` with `baseline: fail` (asserts nothing) | baseline: passes at base | `plan approve` |
| A test that asserts nothing, covering a scenario | the reviewer; and if it is outcome evidence, controls + mutation | ticket gate, integration |
| Oracle or plan edited after approval | snapshot digest | `run`, every round |
| Missing receipt | acceptance: UNKNOWN (missing) | `verify` |
| Receipt for another tree or digest, or edited | acceptance: UNKNOWN (stale) | `verify` |
| Delivered source differs from the verified tree | integration pins the SHA; archive re-runs on its head | integration, archive |
| All tickets COMPLETE, outcome FAIL | REJECTED, no archive, Lead request | integration |

## Migration

- Markdown plans in flight keep running on the legacy path (D9) until T11; their status still goes into the md cells
  so the panel keeps working until T10.
- Converge's checks move into `verify` in T4 with the same verdicts on md plans; the skill copy goes in T9; the
  engine copy goes in T11.
- Old ledgers under `<state>/<slug>.json` are imported once into `<repo-key>/<slug>` (T3).
- Report contract 3 adds `covers`; the driver keeps reading 1 and 2 (md plans).
- No converter. A plan that wants EEC is rewritten as YAML by start-planning.

## Performance

- Invariants: git diff plus file reads, under a second per gate.
- Evidence: per item, one baseline run and one integration run; ticket and archive runs only where routed; no
  automatic reruns. For this plan's own outcome oracle the integration run is a few seconds of fixture work plus a
  warm `uv run` (no measurement yet; T5 records durations in receipts).
- Mutation: one reviewer call plus one run per uncalibrated outcome item (this plan: two items).
- Planning: one oracle-reviewer call per plan.

## Out of scope

- Deferred oracles written after an interface ticket (D4 / Q13 option b).
- Mutation testing beyond the one integration mutation.
- Containers, network isolation, a runner registry, a discovery service, a config file.
- Cross-repo tickets driven by the driver (they are Lead-owned here).
- Renaming the 2,216 existing tagged tests.

## Risks

- **Security:** evidence commands run as the user. Mitigated by approval (a person approves every command), the
  temporary HOME, env by name only, and logs that never print values. Not mitigated: a hostile same-user process (D26).
- **Performance:** a slow outcome check lengthens integration; `timeout` bounds it and UNKNOWN is honest.
- **Migration:** the panel and the in-flight md plans keep their behaviour until T10/T11; contract 3 is additive.
- **Rollback:** each ticket is one PR; reverting T6 returns to archive-on-completion; md plans never depended on
  the new path.

## Seams

- Engine: `RunFixture` / `GateFixture` with `fake_runtime` and `fake_gh` in process (the outcome oracle uses them).
- CLI: `agent-orchestrator plan|plans|status|verify|accept` (contract-first; fixed by S1–S7, S20).
- Hooks: `tests/test_hooks.py` subprocess seam for the worker refusals.
- Skills: the shim's pass-through (`skills/orchestrate/tests/test_delegation.py`).
