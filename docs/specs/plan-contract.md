# Plan contract

The living contract for `plan/1` YAML plans: `plan check`, `plan approve`, evidence, receipts, status and archive. Each requirement below is one scenario of a YAML plan, carrying its provenance as `(from <slug>/S<n>)`; the Coverage table lists the test nodes that prove it.

## Requirements

- **R1** WHEN `plan check <plan.yaml>` reads a plan with an unknown or duplicate key, a missing required field, a duplicate ID, a reference to an undeclared scenario or ticket, a dependency cycle, an evidence item with neither `check` nor `human`, an oracle `place` that escapes the repo or exists already, or a risk-tagged ticket with no evidence-bearing scenario and no `evidence_waiver`, THEN it exits 2 and names each defect with its YAML path and the fix; a valid plan exits 0 (from yaml-eec/S1)
- **R2** WHEN `plan approve` runs on a valid plan, and afterwards plan.yaml (outside `approval`) or a file in its oracle directory changes, THEN approve writes `approval: {by, at, base, digest}` (digest over repo identity, base, the plan and the ordered oracle bytes) and snapshots those bytes under the state dir; after the change `plan check` and `run` refuse, naming the changed file and `plan approve`; no worker is spawned (from yaml-eec/S2)
- **R3** WHEN `plan approve` is invoked by an agent the runtime's dispatch store knows as a spawned worker, THEN it refuses, naming the reason and that approval is the Lead's; nothing is written (from yaml-eec/S3)
- **R4** WHEN an approved YAML plan is launched, THEN its agent tickets dispatch with the class, effort, model and blocking order a Markdown plan with the same rows gets today (from yaml-eec/S4)
- **R5** WHEN `plans list --json` runs with an explicit path, in a repo whose plans sit in one directory (`docs/plans/` or hidden `.plans/`), in a repo with plan files in two directories, and in a repo with none, THEN it lists the explicit plan; that directory's plans; refuses naming both directories and the explicit-path way out, unless the repo's `.orchestrate/config.yaml` names one of them as `plans.dir`, which is then the one listed; an empty list. No directory or config file is created (from yaml-eec/S5)
- **R6** WHEN a plan.yaml outside the repository is passed explicitly with `--repo` to `plan check`, `plan approve` and `run`, THEN all three work, and nothing is written next to the plan except the approval block (from yaml-eec/S6)
- **R7** WHEN a YAML plan runs through dispatch, a pause, a `decide` answer and a merge, THEN plan.yaml stays byte-identical; `status <plan> --json` reports run_dir, the plan state and its history, and each ticket's state, reason and PR, before and during the run (from yaml-eec/S7)
- **R8** WHEN two repositories each run a plan with the same slug, and a ledger under the old `<state>/<slug>.json` key exists, THEN each gets its own ledger under `<state>/<repo-key>/<slug>`; the old ledger is imported once into the repository that owns it (from yaml-eec/S8)
- **R9** WHEN a ticket report (contract 3) maps a satisfied scenario in `covers` to a test node that does not exist or did not change in the ticket, or leaves a satisfied scenario unmapped, THEN verify fails the gate with a fix round naming the scenario, the node and the reason (from yaml-eec/S9)
- **R10** WHEN a ticket's diff touches a file outside its paths, the plan, an oracle file or an oracle place, THEN verify fails the gate naming the file and the rule (scope or integrity) (from yaml-eec/S10)
- **R11** WHEN a Markdown plan in flight is gated, THEN verify's legacy path gives the verdicts converge gives today; the plan can reach COMPLETE (outcome unverified), never ACCEPTED (from yaml-eec/S11)
- **R12** WHEN the driver runs an evidence item, THEN it runs `check` under `bash -euo pipefail` in a detached worktree at the target commit, oracles placed, with a temporary HOME and XDG_STATE_HOME, the real cache dirs, no VIRTUAL_ENV or lead venv on PATH, only the declared env names, and `EEC_JUNIT` set; the receipt names digest, phase, commit, tree, check, oracle sha256s, env names (never values), tool versions, exit, JUnit counts and result; the ledger holds its sha256 (from yaml-eec/S12)
- **R13** WHEN a check exits 0 with JUnit counts showing executed cases and no skips; exits 0 with no cases executed or a selected case skipped or xfailed; fails on an assertion; fails with a collection or setup error; times out; exits 127; names an unset env variable; or leaves a tracked file modified, THEN the result is PASS; UNKNOWN; FAIL; FAIL (error); UNKNOWN (timeout, the process group killed); UNKNOWN (missing tool); UNKNOWN (env); UNKNOWN (dirty tree). A check that writes no JUnit is labelled exit-code-only. Nothing is rerun automatically (from yaml-eec/S13)
- **R14** WHEN `plan approve` runs the baseline at `base`, THEN a `baseline: fail` item must collect without errors, fail at least one case on an assertion and, for a new test oracle, pass at least one case (its controls); a `baseline: pass` item must pass; otherwise approve refuses, naming the scenario, expected and observed, and writes nothing. The receipt records whether the red was calibrated. Scenarios whose items run the same check, oracles, place, env, timeout and negative share one run, each keeping its own receipt; every run shares one worktree at `base`, reset between runs to the commit's tree except its root `.venv` (from yaml-eec/S14)
- **R15** WHEN an evidence item declares a `negative` patch, THEN the runner applies it to a scratch copy and the check must fail there on an assertion; a check that still passes is FAIL (vacuous) (from yaml-eec/S15)
- **R16** WHEN a ticket reports COMPLETE and either is risk-tagged and satisfies a scenario with evidence, or is the ticket that completes an outcome scenario's satisfies set, THEN the driver runs that evidence at the ticket head after the invariants; FAIL or UNKNOWN is a fix round carrying the command and the log tail; other tickets run no evidence (from yaml-eec/S16)
- **R17** WHEN every ticket of a YAML plan is COMPLETE, THEN the driver fetches and pins one default-branch SHA that contains every ticket's merge, runs every evidence item there, and moves DELIVERED → VERIFYING → ACCEPTED (archive may start) or REJECTED (a Lead request to add a ticket, re-verify or human-accept; no archive) (from yaml-eec/S17)
- **R18** WHEN an evidence item is `human`, or the Lead human-accepts a rejected item with `accept <plan> <S-id> --note`, THEN the item is HUMAN_ACCEPTED with the person, time, scope and tree; the plan can reach ACCEPTED_WITH_HUMAN, never ACCEPTED; the archive waits for it (from yaml-eec/S18)
- **R19** WHEN a person merges a ticket whose ticket evidence failed or never ran, THEN the ticket is COMPLETE, flagged unverified; the plan cannot be accepted until that evidence passes at integration (from yaml-eec/S19)
- **R20** WHEN `verify <plan>` computes acceptance and a receipt is missing, was produced for another tree or approval digest, or no longer matches the sha256 the ledger holds, THEN that receipt does not count, the item is UNKNOWN naming the scenario and the reason, and verify exits non-zero (from yaml-eec/S20)
- **R21** WHEN an outcome item with a new oracle was uncalibrated at baseline and passes at integration, THEN a fresh-context reviewer (never an implementer of the plan) writes one behavioural mutation of the delivered code; the runner applies it and the oracle must fail on an assertion; an ineffective mutation gets one more attempt, then the item becomes a human item (from yaml-eec/S21)
- **R22** WHEN verification meets a check that passes at base, a plan or oracle edited after approval, a missing receipt, a receipt for another tree, and a plan whose tickets all completed but whose outcome evidence fails, THEN each is refused with its reason, no worker runs on the edited contract, and none of those plans is ACCEPTED or archived (from yaml-eec/S22)
- **R23** WHEN a one-ticket YAML plan with an oracle-backed outcome is approved, launched and its work reaches the default branch, THEN status history is APPROVED → RUNNING → DELIVERED → VERIFYING → ACCEPTED → ARCHIVED; the integration receipt is PASS for the default branch's tree and the approval digest; the outcome is re-verified on the archive head; the oracle is promoted byte-identical; plan.yaml is unchanged since approval; `verify` exits 0 (from yaml-eec/S23)
- **R24** WHEN a small real YAML plan in a scratch repository is planned with start-planning, approved, orchestrated with real agents, verified and archived, THEN `status --json` shows it ARCHIVED, its receipts exist, and `plan check` still accepts its approval digest (from yaml-eec/S24)
- **R25** WHEN an ACCEPTED or ACCEPTED_WITH_HUMAN plan archives, THEN the driver archives it with no agent: in the archive worktree it places each `promote: true` oracle byte-identical at its place, copies plan.yaml, its narrative and its oracle directory byte-identical, appends the spec section, commits on `feat/<slug>-archive`, pushes and runs `gh pr create`, and the printed url is the archive unit's PR; it then re-runs the outcome evidence on the archive head, and the plan is ARCHIVED when that PR merges (from yaml-eec/S25, deterministic-archive/S1)
- **R26** WHEN the orchestrate shim is asked for `plan check`, `plan approve`, `plans list`, `verify`, `accept` or `status`, THEN it hands them to the member unchanged, and the agent-skills tree carries no converge skill (from yaml-eec/S26)
- **R27** WHEN start-planning writes a Python oracle for a repository whose formatter is configured (ruff format in pyproject.toml), THEN the oracle is formatted as that formatter formats its promoted path (`ruff format --stdin-filename <place>/<name>.py`) before `plan check` and `plan approve`, so the byte-identical copy promoted at archive passes the repository's format gate (from yaml-eec/S30)
- **R28** WHEN a Markdown plan is passed to `run` after the legacy path is removed, THEN it is refused naming the YAML format and `plan check`; the converge adapter and the plan-cell writer no longer exist (from yaml-eec/S28)
- **R29** WHEN the driver writes the archive's spec section, THEN the plan's `spec` keeps its text and gains `## Requirements: <slug>` (one `- **R<n>** WHEN <when>, THEN <then> (from <slug>/<id>)` per scenario the spec does not hold, numbered from the highest `R<n>` in that file plus one; omitted when it holds every scenario) and `## Coverage: <slug>` (`| Requirement | Scenario | Test nodes |`, one row per scenario: the tickets' `covers` then its placed oracle paths joined by `<br>`, or `human: <evidence>`); a held scenario keeps its number and a missing spec file is created holding the section alone; a scenario with neither `human` evidence nor a node asks the Lead (`retry`, `skip`) and opens no PR; an outcome failure or a conflict on the archive PR asks the Lead the same way and spawns no worker (from yaml-eec/S29, deterministic-archive/S2–S5)
- **R30** WHEN `plan check` reads a plan where a risk-tagged ticket with no `evidence_waiver` satisfies a scenario whose `check` evidence has `baseline: pass` and no `negative`, THEN it exits 2 naming `scenarios[<i>].evidence` and the fix (add a `negative` patch that breaks the behaviour); the same plan with a `negative`, with `baseline: fail`, with `human` evidence, with an untagged ticket or with a waiver stays valid (from yaml-eec-gaps/S1)
- **R31** WHEN `plan schema` runs, THEN it prints the plan/1 JSON Schema with `additionalProperties: false` at the top level and exits 0 (from yaml-eec-gaps/S2)
- **R32** WHEN a receipt is rewritten in place after the ledger recorded its sha256, with its digest, tree and result kept (what a Pi worker, which has no hooks, could do), THEN `verify` does not count it: the item is UNKNOWN naming the scenario and that the receipt no longer matches the sha256 the ledger holds, and verify exits non-zero (from yaml-eec-gaps/S3)
- **R33** WHEN a person ticket that read "needs you" is set COMPLETE in the ledger and the driver runs again, THEN the driver rewrites attention.md from the ledger on every tick: the completed ticket's line is gone, a ticket still waiting is listed once, and a run with nothing waiting has the header only (from yaml-eec-gaps/S4)
- **R34** WHEN the agent-orchestrator package is imported or searched for `wait_checks`, THEN `agent_orchestrator.wait_checks` does not exist and nothing under packages/ names it (from yaml-eec-gaps/S5)
